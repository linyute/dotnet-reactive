# Rx.NET v5.0 之後的版本原則

在撰寫本文件時（2023 年初），`System.Reactive` 的最新可用版本是於 2020/11/10 發布的 [v5.0.0](https://www.nuget.org/packages/System.Reactive/5.0.0)。本 ADR 描述了後續版本的原則。

## 狀態

已接受


## 作者

@idg10（[Ian Griffiths](https://endjin.com/who-we-are/our-people/ian-griffiths/)）。


## 背景

在 Rx 的大部分歷史中，其版本號碼代表了函式庫中的變更。Rx 3.0 是第一個支援 .NET Core (v1.0) 和 .NET Standard 的版本。Rx 4.0 獲得了主要版本號碼升級，因為它引入了對 NuGet 套件的重大重組。[Rx 5.0](https://github.com/dotnet/reactive/releases/tag/rxnet-v5.0.0) 利用了可為 Null 的參考型別，並新增了 `.netcore3.1` 作為目標（因為在 Rx 先前支援的任何舊目標中都無法使用可為 Null 的參考型別）。

這個特定的版本也宣稱自己是「.NET 5.0 發布浪潮的一部分」。確實，它的發布是為了配合 .NET 5.0 的發布，但 Rx 自己的版本號碼在那時剛好達到 5.0 完全是一個巧合。這產生了一種相當不幸的看法，認為 Rx 的版本號碼應該繼續遵循 .NET 的版本號碼，即使沒有充分的技術理由這樣做。

重要的是要理解，NuGet 套件列出的*目標*與支援該套件的架構之間存在區別。最明顯的範例是針對其中一個 .NET Standard TFM（目標架構 Moniker，例如 `netstandard2.0`）的函式庫。沒有名為「.NET Standard 2.0」的 .NET 版本。相反地，有多個 .NET 執行階段都能夠使用以 `netstandard2.0` 為目標的函式庫。

更微妙的一點是，當 TFM *確實*與 .NET 的特定實作一致時（例如，`netcoreapp3.1` moniker 與 .NET Core 3.1 相關聯），也有多個 .NET 執行階段能夠使用這樣的函式庫。這是一個引起混淆的點。[.NET Core 3.1 執行階段於 2020 年 12 月 13 日終止支援](https://learn.microsoft.com/en-us/lifecycle/products/microsoft-net-and-net-core)。因此，當人們在 NuGet 上看到以 `netcoreapp3.1` 為目標的函式庫時，很容易認為該函式庫現在已經過期。但事實並非一定如此：在撰寫本文件時（2023 年初），.NET 6.0 和 .NET 7.0 目前都在支援範圍內，且這兩者都支援載入 TFM 為 `netcoreapp3.1` 的函式庫。因此，`netcoreapp3.1` 在今天對於函式庫來說是一個完全有效的目標，並不一定意味著該函式庫已過期。對於一個全新的函式庫來說，這將是一個稍微奇特的 TFM 選擇，但儘管如此它仍然是有效的。（而且有些開發人員發現自己處於必須保持舊系統運行的情況，即使這些系統在技術上已不受支援，因此函式庫有時有充分的理由使用這些較舊的 TFM。）

Rx 處於 5.0 版本，以及其特定於 .NET 版本的 TFM（`netcoreapp3.1`、`net5.0` 和 `net5.0-windows10.0.19041`）似乎都指向現在已不受支援的 .NET 版本，這兩者的綜合影響導致了一種認知，即 Rx 在某種程度上「落後了」。人們錯誤地得出 Rx 無法在 .NET 6.0 或 .NET 7.0 上運作的結論。事實上 Rx 5.0 在這些執行階段上運作得非常好。

一個可行的選擇是直接接受許多開發人員對執行階段版本、TFM 和 NuGet 套件版本號碼之間的區別，或 TFM 的相容性規則沒有足夠深入的了解，並在每次推出新版 .NET 時都提高您的版本號碼，即使這樣做完全沒有技術上的合理解釋。這種做法有其可取之處：與嘗試解釋相關事實相比，這可能是滿足抱怨的開發人員的更有效方法。但這本質上是在使用技術機制來解決心理社會問題（提高版本號碼純粹是為了阻止人們抱怨），這充其量是一種令人不滿意的策略。此外，這種方法有一個缺點：不必要的版本激增增加了複雜相依性樹中版本衝突的機會。（值得注意的是，即使是 `Microsoft.Extensions.*` 套件也略微放棄了嚴格遵循 .NET 版本號碼的政策。在 .NET Core 3.1 中，為每個*修補*層級的更新都發布了一組全新的元件。因此您會在 `Microsoft.Extensions.*` 領域中找到每個套件的 3.1.0、3.1.1、3.1.2、3.1.3 等等，儘管這些版本中的絕大多數除了版本號碼之外在所有方面都與其前身相同。對於 6.0 和 7.0 版本，只有在真正發生變更時才會發布新版本。因此，某些套件的 v7.0.1 肯定與 v7.0.0 不同。）僅遵循執行階段版本號碼的政策也使得判斷某些內容何時真正發生變更變得更加困難。從 v6 升級到 v7 是否像語意化版本控制規則所暗示的那樣意味著重大變更？或者該套件只是盲目地遵循執行階段的版本編號？

## 決策

從 Rx v6.0.0 開始，Rx 的版本號碼不與 .NET 版本掛鉤。（它們可能會不時地剛好一致，但這種巧合在技術上沒有任何意義。）

Rx v6.0.0 將支援 .NET 6 和 .NET 7。（它可能沒有任何 `net7.0` TFM，但它將在 .NET 7 上經過完整測試並得到明確支援。）

如果重大變更變得必要，Rx 的主要版本號碼將根據一般的語意化版本控制規則進行提升。同樣地，如果以向下相容的方式新增了新功能，則將提升次要版本號碼。不變更 API 介面的錯誤修復將僅提升版本號碼的第三部分，例如 v6.0.1 將表示具有與 v6.0.0 相同的 API 介面但修復了錯誤的套件。

v6.0.0 發布版本移除了特定於較舊且不受支援之 .NET 執行階段的 TFM。v5.0.0 包含 `netcoreapp3.1` 和 `net5.0` 目標，而 v6.0.0 將不包含任何早於 `net6.0` 的 .NET 版本專屬 TFM。我們將繼續提供 `netstandard2.0`，因此在技術上可以在某些不受支援的執行階段上執行 Rx 6.0。但是，我們將僅在仍受支援的執行階段上進行測試，這意味著我們將不會以任何官方方式支援在 .NET Core 3.1 或 .NET 5.0 上使用 Rx 6.0。取消支援實際上是一項重大變更，這就是我們提高主要版本號碼的原因。

取消對不受支援架構的測試，部分是由於使 Rx 的程式碼庫與當前工具鏈保持一致的行動所推動的（例如，請參閱 https://github.com/dotnet/reactive/pull/1882）。我們預計將來隨著執行階段失去支援以及工具鏈的向前發展，類似的變更將是必要的。因此我們的原則是，如果發布的 Rx 不包含其前身所包含的目標，出於語意化版本控制的目的，我們將其視為重大變更。

新增對新版 .NET 的支援（無論是否伴隨在 NuGet 套件中新增目標）不需要提升主要或次要版本號碼。此類支援通常將透過在測試專案中新增目標來建立。如果在針對新版 .NET 測試 Rx 的過程中，我們發現有必要進行變更，我們將提升修補版本。（例如，如果在 .NET 8 發布時 Rx v6.0.0 仍然是 Rx 的目前版本，且我們發現有必要變更 Rx 的內部行為以在 .NET 8 上正常運作，我們將把版本號碼設定為 Rx 6.0.1，因為我們認為這是一個錯誤修復。）


## 後果

Rx 的下一個版本（我們計畫成為第一個明確支援 .NET 6 和 .NET 7 的版本）將是 v6.0。

如果解決 Avalonia 等專案在使用 Rx 時遇到的問題（請參閱 https://github.com/dotnet/reactive/discussions/1868 的 *Roadmap and Architectural Decisions* 區段）所需的變更需要重大變更（這似乎很可能），則解決此問題的 Rx 版本將是 v7.0（除非有某些原因迫使我們在解決該問題之前進行另一次主要版本號碼提升）。
