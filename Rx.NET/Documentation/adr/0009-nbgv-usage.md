# Rx.NET 如何使用 Nerdbank.GitVersioning

Rx.NET 使用 [Nerdbank.GitVersioning](https://github.com/dotnet/Nerdbank.GitVersioning) (`nbgv`) 來產生用於 NuGet 套件的版本號碼、各種檔案版本號碼和屬性、Azure DevOps 建構和發布號碼，以及 GitHub 版本名稱。

我們以一種稍微非標準的方式使用 `nbgv`。本文件解釋了導致這種情況的壓力，並解釋了我們做了什麼以及為什麼這樣做。

## 狀態

既成事實（_Fait accompli_）。（本 ADR 是對多年來一直存在之做法的回溯性解釋。）

## 背景

為了安全地使用函式庫，開發人員需要知道它來自哪裡。惡意行為者建構廣泛使用的函式庫之修改版本並誘騙開發人員使用它們的供應鏈攻擊，已被證明具有極大的破壞力。防範此類攻擊的一項至關重要的防禦措施是讓使用軟體元件的開發人員易於了解該元件的來源。

### nbgv 如何提供協助

來自 https://github.com/dotnet/Nerdbank.GitVersioning/blob/main/README.md 的這段陳述是 `nbgv` 哲學的核心：

> 每個 commit 都可以建構並產生唯一的版本。

由於 git commit 與版本號碼之間存在 1:1 的關係，因此對於函式庫的任何特定複本，其版本都與一個特定的 git commit 相關聯。您執行的程式碼絕不應該有任何疑問。

當然，惡意行為者可以自由地將版本號碼設定為他們想要的任何內容。但是因為我們為任何單一版本發布了恰好一組二進位檔案（並且我們對程式碼進行了簽署），所以可以檢查任何聲稱是 Rx.NET 版本的檔案並確認它是否確實是。首先檢查它是否已使用 `Reactive Extensions for .NET (.NET Foundation)` 憑證（進而由 .NET Foundation Projects Code Signing 憑證授權單位認證）進行簽署。然後檢視其版本號碼。在 GitHub 中找到該版本的 release。您現在確切知道所使用的函式庫是從哪一個 commit 建構的。（如果您想交叉核對——也許您懷疑有人嘗試過供應鏈攻擊並希望完全消除疑慮——您還可以檢查您擁有的二進位檔案是否與我們隨該版本發布的檔案在位元組層級完全相同。此外，您可以透過檢視 `Product version` 來找到建構任何 Rx.NET DLL 時所對應的 commit。您可以透過在 Windows 檔案總管中以滑鼠右鍵按一下 DLL，選取「內容」並移至「詳細資料」索引標籤來找到它。對於 `System.Reactive.dll`，這將是 `6.1.0+f4da16f15a`。這與 [GitHub 上的 6.1.0 版本](https://github.com/dotnet/reactive/releases/tag/rxnet-v6.1.0) 所回報的 commit 一致。您還可以在 [NuGet Package Explorer](https://nuget.info/packages/System.Reactive/6.1.0) 中看到任何 Rx.NET NuGet 套件的完整 SHA。Package Explorer 的目前版本會在左側的 Misc 區段中顯示它。）

`nbgv` 實現這種嚴格的 commit:version 對應的方法之一是在版本產生演算法中避免依賴 tag 或分支名稱。這兩者都可能隨時間變更。（事實上，分支的正常做法是端點一直在變更；tag 通常預期不會變更，但它們可以變更，這使它們成為建立來源出處之不可靠方式。）`nbgv` 命令列工具可以在其提供的一些公用程式中考慮分支名稱，但這是為了方便協助您修改 `version.json` 而做的，並不影響核心版本產生演算法：該演算法僅考慮您選擇 commit 的變更。

無論如何，我們不使用 `nbgv` 的這些便利功能。它們實際上對我們不起作用，因為它們做出了一個對此儲存庫不成立的假設。

### 不受歡迎的 nbgv 假設

當涉及到 Rx.NET 時，`nbgv` 存在一個問題：它對版本號碼的第 3 部分（[語意化版本控制](https://semver.org/)稱之為 _patch_，而 .NET 的 [`Version`](https://learn.microsoft.com/en-us/dotnet/api/system.version) 型別稱之為 _build_）的呈現方式做出了假設。它假設您樂於讓它反映歷史的偶然性，導致版本號碼看起來與我們歷史上在 Rx.NET 中所做的任何事情完全不同。

例如，第一個 `major.minor` 版本為 `5.0` 的 Rx.NET 版本的 NuGet 版本為 `5.0.0`，而 .NET 組件的版本皆為 `5.0.0.0`。同樣，下一個主要版本的 NuGet 和 .NET 組件版本為 `6.0.0` 和 `6.0.0.0`。我們發布了兩個錯誤修復的 `6.0` 版本，NuGet 版本為 `6.0.1` 和 `6.0.2`。（對於這些版本，.NET 組件版本仍保留為 `6.0.0.0`，因為您通常不希望該版本隨錯誤修復版本而變更。）

我們的觀點是這些類型的版本號碼清楚地傳達了意圖。顯而易見 `6.0.0` 是 `6.0` 版本中的第一個。顯而易見 `6.0.1` 是 `6.0` 系列中的第一個錯誤修復版本。

但是將其與以 `nbgv` 預期使用方式使用 `nbgv` 的專案進行比較。這裡顯而易見的選擇是 [`nbgv` 本身](https://www.nuget.org/packages/Nerdbank.GitVersioning)。以下是最近的版本號碼（在撰寫本文時）：

* `3.7.112`
* `3.7.115`
* `3.8.118`
* `3.9.50`
* `3.10.70`
* `3.10.85`

那是從 2024 年 12 月到 2026 年 6 月的每個公開版本。這些在技術上沒有任何問題，但我發現這些版本的第三部分令人分心。當我第一次看到 `3.9.50` 時，我想：哇，他們一定發布了很多版本；我最好去確認一下是否沒有更新的 `3.9.x`。事實上，那是唯一的 `3.9.x` 版本。（在我偏好的版本控制美學中，它本應被稱為 `3.9.0`。）而在 `nbgv` 在特定的 `major.minor` 中發布了多個修補程式版本的情況下，您無法從這些數字推斷出太多資訊：`3.7.112` 和 `3.7.115` 版本（差異為 3）相隔大約一個月，但 `3.10.70` 和 `3.10.85`（差異為 15）是在同一天發布的！

顯然，`nbgv` 的作者除了表達一個版本比另一個版本更新這一事實之外，並沒有試圖透過該 patch/build 版本元件向取用端傳達任何資訊。

這是有原因的：`nbgv` 嘗試提供一個即使在從預覽版轉移到正式版時也會增加的版本號碼。例如，您可能會看到 `7.0.1-preview`，然後是 `7.0.2-beta`，然後是 `7.0.3`。從每天處理專案的開發人員的角度來看，您會得到一個看起來完全合理的版本號碼序列，因此當 patch/build 位置出現帶有 `50` 的公開版本時，它看起來一點也不突兀——您每天都在程式碼庫中，所以您知道達到當前狀態之前的 49 個前置 commit。

但是對於函式庫的取用端來說，版本號碼的這一部分大多是雜訊。它提供的唯一有用資訊是，如果您對特定 `major.minor` 版本確實有多個版本，則編號較高的版本是最新的。但是像 `3.7.112` 和 `3.7.115` 這樣的版本對函式庫取用端來說不如 `3.7.0` 和 `3.7.1` 提供更多資訊（在後者中完全清楚這分別是第一個 `3.7` 版本和第一個錯誤修復 `3.7` 版本）。

我還發現第三個位置的雜訊使得更難看到重要資訊：我必須檢視該版本號碼清單更長時間才能理解它，而如果它是這樣的話：

* `3.7.0`
* `3.7.1`
* `3.8.0`
* `3.9.0`
* `3.10.0`
* `3.10.1`

這並不是說 `nbgv` 是錯的。它沒有錯。它做出了邏輯上合理的選擇。只是這不是我們希望我們的版本號碼看起來的樣子。我們希望付出額外的努力使版本號碼減少雜訊並提供稍微更多的資訊。


### 在 nbgv 中控制版本

`nbgv` 提供了一個應急出口：您可以透過多種方式強制它發出所需的版本號碼。但是，由於這不是該工具的作者使用該工具的方式，因此您是在逆流而上。`nbgv` 命令列工具的一些便利功能變得無法使用。（例如，我們不能使用它的 `prepare-release` 命令。）把事情搞錯也是非常容易的。

例如，Rx.NET 的 `6.0.0` 版本在 GitHub 中被標記為 [6.0.0.1](https://github.com/dotnet/reactive/releases/tag/rxnet-v6.0.0.1)，因為 `nbgv` 的行為超出了我的預期。事實證明，它真的很想在某處新增基於*高度*（height）的版本元素，因此如果您告訴它版本明確為 `6.0.0`，`nbgv` 會想：太好了——您將版本的第 4 部分保持未使用，所以我可以把基於高度的部分放在那裡。

（在 `nbgv` 中，*高度*（height）是指自您上次在組態中明確設定版本號碼以來的 commit 次數。這會產生自動增加的版本號碼。我們在預覽版編號中依賴它。例如，[7.0.0-preview.20](https://www.nuget.org/packages/System.Reactive/7.0.0-preview.20) 中的 `20` 是由 `nbgv` 基於高度的機制產生的。我們不介意預覽版編號中的間隙，因為它們實際上提供了資訊——您可以大概了解預覽版之間發生了多少變更。這對大多數開發人員來說並不是很有趣，但如果您選擇透過使用預覽建構來體驗最新尖端技術，您可能確實想知道預期的變更程度。高度在預覽版中是相關的，因為正常的語意化版本控制保證不適用於預覽版，因此您從版本的主要部分獲得的資訊比不使用預覽版時要少。）

如果您完整指定了 4 個位置的版本號碼，您就沒有給 `nbgv` 留下空間，然後它就不會發出基於高度的版本。但是，如果您希望發布的版本具有 3 部分的版本號碼，這對您沒有幫助。我希望在 NuGet 中顯示為 `6.1.0` 的版本在 GitHub 中被標記為 `6.1.0`，而不是 `6.1.0.0`（或者正如 `nbgv` 所選擇的 `6.1.0.1`）。

為了避免這種情況，您本質上必須迎合 `nbgv`：您需要讓它認為它已經表達了高度。如果您檢視 Rx.NET 6.1 版本，特別是 [對 `version.json` 的此項變更](https://github.com/dotnet/reactive/commit/f4da16f15a3cde97f178396ea6e3489cc893651f)，您將看到我們實際上將版本號碼設定為僅有兩部分：

```json
"version": "6.1",
```

這樣，`nbgv` 可以認為它將版本的第 3 部分作為基於高度的 commit 發出，然後它就滿意了。但是因為我們實際上希望這是 `6.1.0`，我們在該檔案稍後使用了稍微笨拙的應急出口：

```json
"versionHeightOffset": -1
```

這告訴 `nbgv` 我們想要調整基於高度的數字。由於此 commit 對 `"version"` 進行了重大變更，因此 `nbgv` 認為這是*版本基準*（_version base_），這意味著它成為 `6.1.x` 版本基於高度計數的起點。但是 `nbgv` 從 `1` 開始計數，這是通常只有人類才會表現出的奇怪習慣。由於我們希望第一個版本是 `6.1.0`，我們將高度偏移設定為 `-1`（否則 `nbgv` 會選擇 `6.1.1`）。我們很高興，因為我們得到了我們想要的版本號碼；`nbgv` 很高興，因為它認為它可以根據高度確定版本的一部分。

嗯，我們差點就完全滿意了。

### 其他檔案版本

除了 NuGet 和 .NET 組件版本之外，`nbgv` 還設定了幾個額外的版本：

* `AssemblyFileVersion`（它也進入 PE 標頭，並且是在 Windows 檔案總管的「檔案內容」中可見的版本）
* `AssemblyInformationalVersion`

在 Rx 6.1.0 中，後者設定為 `6.1.0+f4da16f15a`。那是 [`6.1.0` 版本的 commit](https://github.com/dotnet/reactive/commit/f4da16f15a3cde97f178396ea6e3489cc893651f) SHA 的前 10 個數字。如前所述，這使得很容易查看使用哪個實際 commit 建構了此版本的元件。我們對此感到滿意。

但是，當我研究這個問題以便最終正確記錄我們如何做到這一點時，`AssemblyFileVersion` 值令人意外。（這是 Windows 檔案總管回報為**檔案版本**的數字。）在 `6.1.0` 版本中它設定為 `6.1.0.62682`。我以前從未注意到檔案版本的最後一個位置似乎有一個隨機數。早在 v4.0.0 就是如此（儘管奇怪的是，v5.0 是個例外：它在這裡具有 `5.0.0.1`）。

我無法找到有關此問題的任何文件，但是單步執行 `nbgv` 的原始程式碼揭示了答案。如果 `nbgv` 認為它將高度放在版本的第 3 部分，它總是將 `AssemblyFileVersion` 的第 4 部分設定為從 commit 雜湊衍生的數字。似乎沒有任何直接的方法來設定此行為；您可以透過阻止 `nbgv` 將高度放入版本的第 3 部分來防止這種情況，但是如果您這樣做，非預覽版發布的名義版本號碼最終將具有 4 個部分，從而導致類似 `6.0.0` 版本被標記為 `6.0.0.1` 的異常情況。

我認為這是為了處理類似我們在預覽版本中所遇到的情況。因為我們沒有使用 `nbgv` 偏好的為每個發布版本提供不同 patch/build 編號的方法，我們的預覽版獲得了類似 `7.0.0-preview.1`、`7.0.0-preview.15` 等版本。（我們將高度放在發布前標籤之後。如果我們按照 `nbgv` 偏好的方式進行，這些將被稱為 `7.0.1-preview`、`7.0.15-preview` 等。）如果不是因為 `AssemblyFileVersion` 從 commit 雜湊衍生的最後一部分，每個 `7.0.0-preview.X` 版本都將具有 `7.0.0.0` 的檔案版本，最終的 `7.0.0` 版本也是如此。但是透過放置一個基於 commit 的數字，每個版本都會獲得一個 Win32 工具可以看到是不同的版本號碼。（PE 檔案版本格式需要四個整數，因此無法表達任何等同於 semver prerelease 標籤的內容。）這稍微有些粗糙，因為在此版本記錄中沒有足夠的位元來保證唯一性；毫無疑問，`nbgv` 的作者會說這正是為什麼我應該讓 `nbgv` 做它想做的事情，為每個不同的建構增加 `patch`/`build` 版本，但我已經討論過為什麼我們不想這樣做。理想情況下，我會為預覽版提供基於雜湊的版本，但在最終版本中將其固定為 `7.0.0.0`，但 `nbgv` 工具沒有提供執行此操作的方法。

## 決策

關於 `AssemblyFileVersion` 的 commit 衍生最終部分，我們只能接受雖然它看起來很奇怪，但我們無法變更它，因為任何可以修復此問題的 `nbgv` 組態變更都會導致其他更嚴重的問題。

解決了這個問題之後，我們轉向本 ADR 中決策的主要部分。對於進行中的開發工作與發布準備，我們有不同的程序。

### 日常開發（預覽版發布）

對於日常開發，我們在 `main` 中的 `version.json` 看起來像這樣：

```json
{
  "version": "7.0.0-preview.{height}",
  "publicReleaseRefSpec": [
    "^refs/heads/main$", // 我們從 main 發布
    "^refs/heads/rel/v\\d+\\.\\d+", // 我們也發布以 rel/vN.N 開頭的分支
    "^refs/heads/rel/rx-v\\d+\\.\\d+" // 我們也發布以 rel/vN.N 開頭的分支
  ],
  "nugetPackageVersion":{
    "semVer": 2
  }
}
```

那裡的 `version` 規格意味著 `nbgv` 基於高度的自動版本控制為我們提供了一個持續遞增的版本號碼流，而不需要我們變更 `version.json`。我們明確告訴它將高度放在最末端（這足以滿足 `nbgv` 確信它必須在*某處*發出高度的想法）。

發布參考規格反映了我們的分支命名，以便 `nbgv` 知道這是否打算作為公開版本。對於非公開版本，`nbgv` 始終在版本中新增雜湊以確保在跨多個分支並行開發時的唯一性。（您可以在 [Rx.NET 預覽套件摘要](https://dev.azure.com/dotnet/Rx.NET/_artifacts/feed/RxNet/NuGet/System.Reactive/versions/7.0.0-rc.1) 中看到範例，例如 `7.0.0-preview.20.g9ca7a5f26b`。）如果沒有它，在多個分支上進行的並行工作可能會破壞 commit 計數本應提供的唯一版本保證。`nbgv` 需要知道哪些分支旨在整合來自此類並行開發的變更。純粹基於高度的版本號碼依賴於線性進度的假設，這僅真正適用於整合分支，而不適用於主題分支，因此我們必須告訴 `nbgv` 那些分支是什麼。它將考慮任何其他分支為非公開的，因此它將在版本中納入 SHA 的前 10 個數字以確保唯一性。（例如，為開啟的 PR 產生的建構始終包含此基於 SHA 的元件。）

其效果是，當我們合併到 `main` 時，這會產生一個名稱類似 `7.0.0-preview.20`（不帶雜湊）的版本，如果我們決定這樣做，該版本適合發布到 NuGet.org。

（該檔案還反映了一個事實，即回溯一段時間，我們過去常常不在分支名稱中放置 `rx`。我們現在可能可以將其刪除，因為我們永遠不會回去為那麼舊的任何版本進行錯誤修復。）

`"semVer": 2` 告訴 `nbgv` 它不需要支援無法理解像 `7.0.0-preview.15` 這樣版本的古代工具。

### 新的主要或次要版本

當我們第一次想要產生某個 `major.minor` 時（例如，如果 `7.0.0` 已經發布並且我們打算產生 `7.1.0`），我們建立一個名稱包含主要和次要版本的新分支，例如 `rel/rx-v7.1`。

**注意**：如果您按預期使用 `nbgv`，可以使用其 `nbgv prepare-release` 來執行此操作。我們沒有這樣做，因為它似乎假定您將能夠推送到 `main`。`prepare-release` 執行四件事：1) 建立新的發布分支，2) 更新該發布分支上的 `version.json`，3) 修改 `main` 上的 `version.json` 以產生更高的版本號碼，4) 以某種方式合成一個合併 commit，這意味著如果您在發布分支上進行任何修復並隨後將其合併回 `main`，該合併將不會產生嘗試將在發布分支上進行的 `version.json` 變更套用至 `main` 的副作用。我們在 `main` 上有分支保護，因此步驟 3 和 4 對我們來說不太適用，而且事實證明我們還需要修改它在步驟 2 中所做的變更。因此對我們來說不使用 `prepare-release` 更容易。

我們可能會決定不直接從 `preview` 轉到最終版本。我們避免使用 `beta`，因為 NuGet 套件管理員在檢視標籤後面的數字之前按字母順序對預先發行標籤進行排序，這意味著它認為 `7.1.0-preview.20` 是比 `7.1.0-beta.21` 更新的版本。因此我們改用 `rc`。（`7.1.0-rc.1` 排序為比 `7.1.0-preview.20` 更新的版本。）因此我們將擁有：

```json
  "version": "7.1.0-rc.{height}"
```

這會產生版本 `7.1.0-rc.1`。（儘管我們喜歡我們的 patch/build 編號從 0 開始，如在 `7.1.0` 中，但我們確實更喜歡我們的預先發行標籤從 `1` 開始，因此如果使用 `rc` 前綴，我們不設定任何 `versionHeightOffset`。預設值為我們提供了所需的初始版本。）

如果稍後需要 `rc.2`（甚至 `rc.3` 或更多），對此分支的每個 commit 都將產生比上一個更高的版本（但都具有相同的 `7.0.0-rc.` 前綴）。在此階段不需要對 `version.json` 進行進一步更新。

一旦我們為非預覽（最終）版本做好準備，我們對 `version.json` 進行以下變更：

```json
  "version": "7.1",
  ...
  "versionHeightOffset": -1
```

這會導致 `nbgv` 將基於高度的版本作為 patch/build 放入，並且該 `versionHeightOffset` 導致該高度呈現為 0，從而為我們提供所需的 `7.1.0` 版本號碼。

回到 `main` 上，`version.json` 應設定為比新建立的發布分支更高的 `major.minor`，例如：

```json
  "version": "7.2.0-preview.{height}",
```

甚至：

```json
  "version": "8.0.0-preview.{height}",
```

我們不希望的是 `main` 產生 `7.1.0-preview.X` 或 `7.1.1-preview.X` 版本，因為一旦我們建立了 `rel/rx-v7.1` 發布分支，任何 `7.1.X-preview.Y` 版本都應該來自那裡，而不是 `main`（原因是如果兩個分支最終產生相同整體格式的版本，不同分支上的兩個不同 commit 可能會產生具有相同版本號碼的版本，這正是我們試圖透過使用 `nbgv` 避免的情況。）

請注意，由於 `main` 具有分支保護，我們在為此目的建立的新功能分支中更新 `version.json`，然後透過 PR 將其合併到 `main`。

### 新的修補程式版本

如果我們有某些現有的 `major.minor` 並希望具有相同 `major.minor` 的新版本，我們的目標是將 NuGet 套件中的第 3 個版本部分（semver 稱之為 patch）設定為高一位。例如，在 `7.0.0` 之後，我們將需要 `7.0.1`。（這通常僅用於修復錯誤——語意化版本控制需要變更次要或主要版本。）

我們需要做的就是在發布分支（例如 `rel/rx-v7.0`）上建立一個包含錯誤修復的新 commit。（我們的發布分支具有分支保護原則，因此我們無法直接執行此操作。在實務上，您將從發布分支建立一個新的錯誤修復分支，在其中進行修復（可能透過從 `main` 精選 cherry-pick 修復錯誤的 commit），然後建立一個以 squash-commit 合併到發布分支的 PR。）`nbgv` 將遞增修補程式版本，因為現在發布分支上有額外的 commit，因此如果我們之前在 `7.0.0` 上，這將變為 `7.0.1`。

如果在將 PR 壓縮至發布分支後，我們發現修復程式沒有按預期運作，並且產生的函式庫無法使用，我們本質上必須作廢該版本號碼。（希望您在從錯誤修復分支到發布分支的 PR 仍然開啟時就偵測到了該問題。但是錯誤時有發生。）我們的建構和發布流程最初將套件發布到專用的 Rx.NET NuGet 摘要，因此在我們對其進行測試並決定發布之前，內容不會出現在 NuGet.org 上。但是該 Rx.NET 摘要是公開的，任何人都可以從那裡下載套件，因此在該時間點，`7.0.1` 版本將「在外部可用」，即使它從未在 NuGet 上。在這種情況下，我們只能接受我們的錯誤，並在 NuGet.org 上直接從 `7.0.0` 轉到 `7.0.2`。因此，在將 PR 合併到功能分支之前，我們應該盡最大努力絕對確保修復程式按預期運作。

如果錯誤修復旨在解決使用者回報的問題，並且我們沒有信心一次性搞定，我們可能希望在 NuGet.org 上提供預覽版本。這為回報問題的開發人員提供了一種在我們推出修復程式之前對其進行測試的方法。在這種情況下，我們將修改發布分支上的 `version.json` 以恢復預覽標籤。此時我們將使用：

```json
  "version": "7.0.1-preview.{height}",
```

我們在這裡不需要設定 `versionHeightOffset`，因為如前所述，我們絕不應該從 `main` 產生 `7.0.1-preview.X` 版本。（`main` 的 `version.json` 現在應該在 `7.1` 或 `8.0` 或更高版本上。）但是如果出於某種原因犯了該錯誤，那麼我們需要首先修復 `main` 上的 `version.json`，然後選擇一個 `versionHeightOffset`，為我們提供足夠高的起點以保證唯一的版本。

驗證修復程式後，我們將希望產生非預覽的 `7.0.1` 版本。這將意味著再次修改 `version.json`。我們將恢復為 `"version": "7.0"`，並將 `versionHeightOffset` 設定為取得我們想要的版本號碼所需的任何值。（如果我們想要 `7.0.1`，那麼我們想要 `"versionHeightOffset": 0`。對於 `7.0.2`，我們想要 `"versionHeightOffset": 1`，依此類推。請記住，`nbgv` 將變更 `"version"` 的 commit 視為*版本基準*，並認為此時的 commit 高度為 `1`，因此需要設定 `versionHeightOffset` 來彌補差異。）

## 後果

在日常開發期間，每次 PR 合併到 `main` 時，我們都會自動獲得一個新的 `major.minor.0-preview.X` 版本，該版本具有高於前一個預覽版的唯一版本。（這會自動轉到 Rx.NET NuGet 摘要，我們可以選擇發布到 NuGet.org。）因此我們不必在預覽階段考慮版本號碼。

對於非預覽版本，我們能夠控制版本號碼，與歷史實踐保持一致。（即，我們可以擁有 `7.0.0`、`7.0.1`、`7.0.2`、`7.1.0`、`7.1.1`、`8.0.0` 等。）在修補程式版本包含簡單錯誤修復的情況下，如果我們不需要先在 NuGet.org 上提供預覽版，我們可以簡單地將包含修復程式的 PR 以 squash-commit 合併到發布分支中，patch/build 版本號碼將自動遞增。

一個缺點是我們沒有完全按照其作者的預期使用 `nbgv`。這會產生一種風險，即我們可能會意外產生具有相同版本號碼的兩個不同版本。（例如，如果在發布 `7.0.2` 之後，我們產生一個 `7.0.3-preview.1` 以使使用者能夠驗證我們的變更是否修復了他們的問題，那麼在我們準備進行最終發布時就會存在風險。此時的程序是設定 `versionHeightOffset` 以強制 `nbgv` 產生我們想要的 `7.0.3` 版本，但如果我們手動編輯錯誤，我們可能會意外產生另一個與現有 `7.0.2` 版本不同的 `7.0.2` 版本。將其發布到私有 Rx.NET 摘要或 NuGet.org 都是不可能的：兩者都會識別錯誤並封鎖發布。因此這不是一個大問題，但我們將建立並簽署這組假的 `7.0.2` 套件，並且它們在建構輸出中可見。這令人討厭地混亂，但由於 NuGet 摘要會拒絕任何發布嘗試，因此沒有嚴重的後果。）`nbgv` 工具試圖保護我們免受這種情況的影響，但我們否決其版本控制策略的決定意味著現在由我們負責不出錯。

還有一種風險是，因為我們正在做非標準的事情，未來對 `nbgv` 的更新可能會擾亂我們，我們可能需要變更我們的做法。（它已經造成了一些摩擦——花費了大量的實驗才建立了本文件中描述的做法。在將它們寫入本 ADR 之前，很難確切發現我們對以前的版本做了什麼以及為什麼這樣做，從而偶爾引起了不幸事件，例如在 GitHub release 中為 `6.0.0` 帶來不需要的第 4 個發布編號元件。然而，透過記錄我們所做的事情和原因，希望特定的摩擦現在已經成為過去。）
