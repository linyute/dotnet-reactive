# 為 .NET 7.0 時代工具鏈更新 Rx.NET 建構系統

在撰寫本文件時（2023 年初），如果您下載最新版本的 .NET 工具（Visual Studio 2022、.NET 7 SDK 以及 Visual Studio 2022 支援的任何 Windows SDK），是無法在無警告的情況下建構 Rx.NET 的。本 ADR 提出了一組變更以解決此問題。

## 狀態

草案。


## 作者

@idg10（[Ian Griffiths](https://endjin.com/who-we-are/our-people/ian-griffiths/)）。


## 背景

有四個主要問題阻止了 Rx.NET 在目前的工具鏈上進行建構：

* 已不受支援的 TFM
* 使用 Visual Studio 2022 不支援的 Windows SDK 版本
* 新的分析器診斷訊息
* UWP 測試執行器專案（`Tests.System.Reactive.Uwp.DeviceRunner.csproj`）由於與 Coverlet 不相容而建構失敗，且一旦修復該問題，xUnit 似乎無法執行測試

以下各節更詳細地描述了各個方面。

### 已不受支援的 TFM

下表中的目標架構 Moniker（TFM）均已停止支援。該表顯示了哪些專案使用了它們。

| 已不受支援的 TFM | 專案 |
|---|---|
| `netcoreapp2.1` | `Tests.System.Reactive` |
| `netcoreapp3.1` | `Microsoft.Reactive.Testing`、`System.Reactive`、`Tests.System.Reactive` |
| `net5.0` | `Microsoft.Reactive.Testing`、`System.Reactive`、`System.Reactive.Observable.Aliases` |
| `net5.0-windows10.0.19041` | `System.Reactive` |

還有一個更微妙的問題：`netstandard2.0` TFM 當然仍然非常受到支援，但就其目前的型態而言，為該目標建構的 `System.Reactive` DLL 無法在支援 `netstandard2.0` 的所有 .NET 執行階段上正確執行。這是因為它相依於 `System.Runtime.InteropServices.WindowsRuntime`。`netstandard2.0` TFM 名義上與 `.net6.0-windows` 樣式的 TFM 相容，但該函式庫無法在該執行階段上運作，因為它是針對舊的 WinRT Interop 機制撰寫的，其中 CLR 直接處理 `.winmd` 檔案，而 .NET 6.0 則使用較新的 C#/WinRT 機制來與 WinRT API 進行 Interop。

理論上這應該不是問題，因為使用 .NET 6.0 或更新版本的應用程式最終應該會取得 `System.Reactive` 的 `net6.0` 或 `net6.0-windows10.0.19041` 版本。但是，可以想像某些外掛程式情境可能會過早繫結到 `netstandard2.0`。（舊有的 https://github.com/dotnet/reactive/issues/97 問題就是由類似情況引起的。）如果 `netstandard2.0` 組建碰巧載入到 `net6.0` 執行階段中時確實可以運作，那就更好了。（此外，一個可能的未來方向是讓 `System.Reactive` 透過 `netstandard2.0` 目標支援 .NET 6 和 .NET 7，在這種情況下，移除此相依性將變得絕對必要。）

我們已被要求[啟用修剪（trimming）](https://github.com/dotnet/reactive/issues/1683)，並且有人[建議](https://github.com/dotnet/reactive/discussions/1868#discussioncomment-5018844)在 .NET 6.0 上這只需設定 `IsTrimmable` 建構變數即可。如果這是真的，那麼由於遷移到受支援的 TFM 必然意味著以 `net6.0` 為目標，我們應該看看這是否確實有效。

### Windows SDK 版本

Rx.NET 目前使用兩個 Windows SDK 版本。UWP 目標都使用 `uap10.0.16299` 的 TFM，對應於 10.0.16299 的 Windows SDK 版本，而各種 Windows 專屬的 .NET 5.0 目標都在 `net5.0-windows10.0.19041` 上，對應於 10.0.19041 的 Windows SDK 版本。

Visual Studio 2022 不支援使用 Windows SDK 10.0.16299（該版本於 2017 年推出）。它支援的最早 SDK 版本是 Windows SDK 10.0.18362，這是一個相當舊的 SDK——需要這麼舊版本的最後一個 Windows 版本於 2019 年 5 月發布，並於 2020 年 11 月停止支援。以 10.0.20348 為目標的應用程式將適用於仍受支援的所有 Windows 10 和 11 版本。

### 新的分析器診斷訊息

每個新的 .NET SDK 版本都提供了更廣泛的程式碼品質和樣式分析器。這樣做的一個影響是，當專案升級到新的 SDK 時，它會立即產生大量新的警告和訊息。Rx.NET 也不例外。

### UWP 測試執行器問題

Coverlet 函式庫似乎無法在 Visual Studio 2022 中與 UWP 測試專案一起運作。Visual Studio 拒絕載入方案，並回報此錯誤：

```
C:\repos\reactive\Rx.NET\Source\tests\Tests.System.Reactive.Uwp.DeviceRunner\Tests.System.Reactive.Uwp.DeviceRunner.csproj : error  : The expression "[System.Version]::Parse('')" cannot be evaluated. Version string portion was too short or too long.  C:\Users\fquimby\.nuget\packages\coverlet.collector\3.1.1\build\netstandard1.0\coverlet.collector.targets
```

一旦解決了這個問題，一個新問題就顯現出來：[xUnit 測試執行器似乎無法在 Visual Studio 2022 上運作](https://github.com/xunit/devices.xunit/issues/171)。儘管它成功探索了測試並在 Visual Studio 的測試總管中回報了測試，但它無法執行它們。https://github.com/xunit/devices.xunit 專案多年來沒有任何有實質意義的更新。（其標誌於 2021 年 7 月更新，但最後一次發布是在 2019 年 1 月。）更新的支援似乎不會立即出現。

我們已經完成了一次[實驗性探究，以證明遷移到 MSTest 框架是相對簡單的](https://github.com/idg10/reactive/commit/a6d39f6dabf7d6b342f552831c7413d54f3bc32b)。少數測試失敗，因為它們最終被證明依賴於 xUnit 提供非 Null 的 `SynchronizationContext`。這些測試需要進行檢查——失敗可能代表需要解決的真正問題，但如果不是，我們要麼需要修改測試使其預期與不存在 `SynchronizationContext` 的情況一致，要麼安排在這些測試執行時設定 `SynchronizationContext`（或者可能兩者都做，以便相關測試在有和沒有 `SynchronizationContext` 的情況下都能執行）。

轉向 MSTest 的這項變更有一個令人沮喪的問題：它會在建構期間導致一些非常長的路徑長度。如果您將存放庫複製到路徑長度超過 26 個字元的資料夾中（例如 `C:\Users\jdoe\source\repos\reactive`），您將遇到此問題：https://github.com/microsoft/testfx/issues/1607

這很不幸，因為這意味著 Visual Studio 選擇用於複製存放庫的預設位置將觸發此問題。

## 決策

以下各節說明我們將如何處理上述每個問題。

### 已不受支援的 TFM

在所有過去以 `net5.0` 為目標的專案中，將其變更為 `net6.0`。同樣地，在任何以 `net5.0-windows10.0.19041` 為目標的專案中，將其變更為 `net6.0-windows10.0.19041`。

修改 `Directory.build.targets` 中的項目

移除 `Directory.build.targets` 中參考已不受支援 TFM 的項目。這意味著一些前置處理器常數不再使用。我們應該清理程式碼庫，並移除所有因過去引入它們的目標架構已不存在而不再使用的條件編譯程式碼區段。不再使用的常數有：

* `NETSTANDARD1_0`
* `NETSTANDARD1_3`
* `NETCOREAPP1_0`
* `NETCOREAPP1_1`
* `NETCOREAPP2_1`
* `NETCOREAPP3_1`
* `WP8`
* `NO_CODE_COVERAGE_ATTRIBUTE`
* `NO_SERIALIZABLE`
* `CRIPPLED_REFLECTION`
* `NO_THREAD`
* `NO_TRACE`
* `NO_REMOTING`（Remoting 的可用性仍然是個問題，但未使用此符號，因為所有相關區段都改為使用 `HAS_REMOTING`）

在所有專案檔案中尋找參考不再使用的 TFM 的所有 `Condition` 屬性，並移除相關的 TFM。僅對不再使用的 TFM 起作用的元素應完全移除。

在所有過去以 `net5.0` 為目標的測試專案中，除了將其變更為 `net6.0` 之外，還新增 `net7.0`。同樣地，對於過去以 `net5.0-windows10.0.19041` 為目標的測試專案，除了將其變更為 `net6.0-windows10.0.19041` 之外，還新增 `net7.0-windows10.0.19041`。

移除 `Rx.NET/Source/src/System.Reactive/build/System.Reactive.targets`，因為它僅與 .NET Core 3.1 相關

更新建構管線以安裝 .NET 7 SDK 和 .NET 6 執行階段；移除安裝 .NET Core 2.2 和 3.1 的工作。修改目前在 .NET Core 2.1、.NET Core 3.1 和 .NET 5.0 上執行測試的步驟，改為在 .NET 6.0 和 .NET 7.0 上執行。

將依賴 `System.Runtime.InteropServices.WindowsRuntime` 的程式碼取代為不依賴它也能達到相同效果的程式碼。（這可以透過將與 `typeof(EventRegistrationToken)` 的直接比較取代為透過檢查型別名稱來檢查相關型別的程式碼來實現；可以撰寫同時適用於舊版和新版 WinRT Interop 機制的程式碼。）`EventRegistrationToken` 中目前以 `HAS_WINRT` 為條件的程式碼隨後可以變為無條件的。

在 `net6.0` 和 `net6.0-windows10.0.19041` 目標中，我們將嘗試設定 `<IsTrimmable>true</IsTrimmable>`。在進行非預覽版本發布之前，我們需要驗證這是否具有預期的效果。

### Windows SDK 版本

在任何以 `uap10.0.16299` 為目標的專案中，將其變更為 `uap10.0.18362`。（這組特定變更的目標是讓所有內容在現代工具鏈上建構，同時盡可能少地進行變更。這是滿足這些目標的最小版本變更，這就是我們沒有更新到更新版本的原因。）

變更 `Tests.System.Reactive.Uwp.DeviceRunner` 測試執行器專案以將目標設定為 SDK 10.0.18362。

### 新的分析器診斷訊息

當前 SDK 中更積極的分析器所引起的新的診斷訊息將分兩個階段處理

1. 為了能夠儘早提供下一個版本的預覽組建，我們將初步停用新的診斷訊息
2. 一旦發布了預覽組建，如果新的警告提出了我們想要採納的建議，我們將更新程式碼庫，並新增適當的設定以防止警告建議我們不想要的變更

### UWP 測試執行器問題

與 Coverlet 相關的建構問題可以透過在 UWP 測試專案中設定 `NETCoreSdkVersion` 建構變數來解決。

至於目前缺乏 xUnit 支援的問題，目前看來唯一現實的選擇就是不使用 xUnit。已經完成了一次實驗性探究，以證明遷移到 MSTest 框架是相對簡單的。少數測試失敗，因為它們最終被證明依賴於 xUnit 提供非 Null 的 `SynchronizationContext`。這些測試需要進行檢查——失敗可能代表需要解決的真正問題，但如果不是，我們要麼需要修改測試使其預期與不存在 `SynchronizationContext` 的情況一致，要麼安排在這些測試執行時設定 `SynchronizationContext`（或者可能兩者都做，以便相關測試在有和沒有 `SynchronizationContext` 的情況下都能執行）。

## 後果

這些變更將產生以下正面影響：

1. 將可以下載存放庫，並使用目前的工具鏈（VS 2022 和 .NET 7.0 SDK）開啟、建構和測試 `System.Reactive.sln`，而不會出現錯誤、警告或其他診斷訊息
2. 自動化建構現在將在 .NET 6.0 和 .NET 7.0 上執行測試（除了 .NET Framework 之外）
3. 當我們向 NuGet 發布基於這些變更的元件時，它們將不再以停止支援的架構為目標，並將包含 `net6.0` 目標
4. 如果設定 `<IsTrimmable>true</IsTrimmable>` 被證明就是修剪功能所需的全部內容，這將滿足該需求

對於想要建構方案的任何人，它將提出以下新要求：

1. 存放庫必須複製到路徑長度不超過 25 個字元的位置
1. 必須安裝 Visual Studio 2022
1. 必須安裝 .NET SDK 7.0
1. 必須安裝 Windows SDK 10.0.18362
