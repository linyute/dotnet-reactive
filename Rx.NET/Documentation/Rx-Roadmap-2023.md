# 2023 年 Rx 藍圖

截至 2023 年 2 月，`System.Reactive`（又名 Rx.NET，在本文件中簡稱 Rx）已經沉寂了一段時間。本文件說明了讓它重獲新生的計畫。

## 提案摘要

* 初始的 V.next，我們計畫發布為 [v6.0](#rx-v60)，使建構流程與 TFM 保持最新狀態（捨棄超出支援範圍的目標，如 `netcoreapp3.1` 和 `net5.0`，並以目前的 LTS 等效版本如 `net6.0` 取代），並加入在 .NET 6 和 .NET 7 上的自動化測試
* 平行進行 [`System.Reactive.Async`](#rxasync) 的 NuGet 套件 `alpha` 標籤版本發布工作
* 接續的 V.next.next，我們計畫發布為 [v7.0](#rx-v70)，以解決某些 UI 框架所遇到的程式碼膨脹及相關問題
* 發起一項對待處理議題（backlog）進行分類評估的倡議，並確定應在上述各個版本中解決哪些議題

## 當前問題

我們希望解決五個主要問題。

* 近期沒有任何新版本發布
* 建構系統已落後於目前的工具鏈
* 若將 Rx 與某些現代建構技術（例如獨立式部署與預先編譯）搭配使用，會導致不必要的膨脹
* 待處理的議題積壓已久且遭到忽視
* 此存放庫中的非同步 Rx 程式碼處於實驗狀態，儘管有需求，卻從未以任何形式發布過

請注意，多年來 Rx 一直有自己的版本號碼系列，在 .NET 5.0 發布前夕剛好處於 v4 只是巧合。然而，Rx.NET 5.0.0 發布聲明宣稱自己是「.NET 5.0 發布浪潮的一部分」。這導致了一種不幸的看法，認為每個版本的 .NET 都應該有一個具有相符版本號碼的 Rx 新版本。這在技術上並沒有必要——Rx 5.0.0 在 .NET 7.0 上運作得非常好。這裡真正的問題只是開發已經停滯——雖然有錯誤回報和功能需求，但已經有超過 2 年沒有發布過新的 Rx 版本了。

### 當前工具鏈上的建構問題

用於建構 Rx 的工具（尤其是 .NET SDK 和 Visual Studio）發展相當迅速，其結果是，如果您安裝了最新版本的工具並開啟 `System.Reactive.sln`，您將無法獲得乾淨的建構結果。問題包括：

* 除非您安裝已停止支援的 .NET Core SDK（回溯到 .NET Core 2.1），否則 VS 會抱怨專案以未安裝的 .NET 版本為目標
* 如果您確實安裝了較舊的 .NET 和 .NET Core SDK，Visual Studio 會發出警告，告知您相關的架構已停止支援，並且不會收到安全性更新
* UWP 測試存在許多問題：
  * 由於與正在使用的 `Coverlet.Collector` 版本不相容，啟用在 UWP 上執行測試的專案（`Tests.System.Reactive.Uwp.DeviceRunner.csproj`）無法載入
  * 如果移除對 `Coverlet.Collector` 的參考，Visual Studio 會回報 UWP 測試專案對 `System.Reactive` 和 `Microsoft.Reactive.Testing` 專案的參考是不被允許的（且未說明原因），儘管它似乎仍可進行建構
  * 當您嘗試在 Visual Studio 的測試總管中執行單元測試時，所有 UWP 測試都不會執行——它們只會顯示一個藍色驚嘆號，而沒有提供未執行的原因說明；這是因為 Rx 使用 [xUnit.net](https://xunit.net/) 單元測試工具，而這些工具中的 [UWP 支援似乎已不再運作](https://github.com/xunit/devices.xunit/issues/171)——如果您按照 [xUnit 從頭建立全新 UWP 專案並新增測試的說明](https://xunit.net/docs/getting-started/uwp/devices-runner)進行操作，它將無法運作；自 2019 年 11 月以來，[xUnit UWP 測試執行器](https://github.com/xunit/devices.xunit/commits/master)唯一的更新似乎只是變更了標誌；事實上最後一次發布是在 2019 年 1 月（當時 Visual Studio 2017 仍然是最新版本），存放庫隨後的幾乎所有更新都是 dependabot 更新，而不是新的開發
* 用於建構某些測試的憑證已過期
* 有一些與 C# 的可為 Null 的參考型別功能相關的警告
* 較新的分析器規則會導致出現大量的警告和診斷訊息
* 由於工具版本的變更，Visual Studio 會修改一些與 Xamarin 相關的自動產生檔案

### 某些建構技術導致不必要的膨脹

如果您使用 .NET 建構傳統型應用程式，並且建立了獨立式部署，新增對 Rx 的參考可能會導致將數十 MB 的元件不必要地新增到您的應用程式中。

有幾種情況下，由於使用真正的 `System.Reactive` 時可能會發生的問題，專案實際上內建了自己微型版本的 Rx。Avalonia 團隊就遇到了完全相同的問題（請參閱 https://github.com/AvaloniaUI/Avalonia/issues/9549），結果他們從程式碼庫中移除了 Rx（請參閱 https://github.com/AvaloniaUI/Avalonia/pull/9749），並以這樣一個內嵌版本取而代之。

根本問題在於，目前的 Rx 程式碼庫會向任何以可以使用 WPF 和 Windows Forms 框架的 .NET 形式為目標的應用程式提供這兩個框架的支援。

這為什麼是個問題可能並不明顯。事實上，對於 .NET Framework 來說這不是問題：如果您以 .NET Framework 為目標，您將把應用程式部署到已經具有所有 WPF 和 Windows Forms 元件的電腦上，因為這些元件是作為 .NET Framework 不可分割的一部分安裝的。因此，Rx 內建其支援並沒有真正的壞處——UI 框架專屬的程式碼僅佔 Rx 整體大小的一小部分，而且可以說，將對這些函式庫的支援拆分為獨立的函式庫所帶來的複雜性並沒有實質的元件大小效益。

.NET Core 的前幾個版本沒有提供 Windows Forms 和 WPF。然而，.NET Core 3.0 將這些框架引入了 .NET Core 系列，並且它們繼續在最新的（非 .NET-Framework）.NET 版本中可用。這正是將對這些 UI 框架的支援內建到 Rx 中變得成問題的時候，因為在應用程式安裝程式中包含執行階段函式庫的複本通常有充分的理由。但這意味著採用對 WPF 的相依性可能會導致所有 WPF 函式庫的複本都作為應用程式的一部分包含在內。

Rx 的 NuGet 套件包含 `net5.0` 和 `net5.0-windows` 兩個目標。`net5.0` 目標不包含 Windows Forms 或 WPF Rx 功能，而 `net5.0-windows` 目標則包含。任何以 `net5.0-windows` 為目標的應用程式最終都會獲得 `net5.0-windows` 版本的 Rx，這意味著它最終將依賴 WPF 和 Windows Forms。如果執行在 Windows 上的應用程式使用某些其他 UI 框架（例如 Avalonia），它仍然會以 `net5.0-windows` 為目標，這意味著儘管它兩者都不使用，但最終都會依賴 WPF 和 Windows Forms。在獨立式部署或某些預先編譯情境中，這意味著這些函式庫將作為應用程式的一部分進行部署，而它們的大小有數十 MB！

關於膨脹還有一個問題：要在 .NET 6.0 中使用修剪功能，元件必須以指定可被修剪的方式進行建構。目前沒有這些設定，導致 Rx 無法進行修剪。

## UWP 是一個問題

在繼續提出提案之前，了解 UWP 造成了多少問題，以及了解為什麼儘管存在這些問題 Rx 仍然支援它，這一點非常重要。

[通用 Windows 平台（UWP）](https://learn.microsoft.com/en-us/windows/uwp/get-started/universal-application-platform-guide)最初被構想為一種建構應用程式的方式，這些應用程式不僅可以在一般版本的 Windows（具體而言是引入 UWP 時的 Windows 10）上執行，還可以在各種其他基於 Windows 10 的作業系統上執行，包括 XBox、HoloLens 和（現已停產的）Windows 10 Mobile 平台。

.NET on UWP 有點奇怪。它既不使用舊的 .NET Framework，也不使用目前的 .NET 執行階段。UWP 起源於較早期的 Windows 8 市集應用程式平台（曾短暫但令人難忘地被稱為 Metro），該平台擁有專屬的 CLR。Windows 8 版本的 TFM 為 `netcore`、`netcore45` 和 `netcore451`（不要與 .NET Core 使用的 `netcoreappX.X` 系列 TFM 混淆），且 UWP 可以識別 `netcore50` moniker（這與 .NET 5.0 完全無關），儘管這被認為已棄用，目前更傾向使用 `uap`、`uap10.0` 或特定 SDK 版本的形式（例如 `uap10.0.16299`）。這條特殊的 .NET 系列早在預先編譯（AoT）進入更主流的 .NET 版本之前就支援了它（主要是因為早期基於 ARM 的 Windows 8 裝置需要 AoT 才能提供可接受的應用程式啟動時間）。它還有很多來自讓 Windows 市集應用程式成為「受信任」目標的限制。某些相當基本的功能（例如建立新執行緒）是被禁止的，以防止個別應用程式對小型裝置上的整體系統效能或功耗產生負面影響。

這給需要處理執行緒的函式庫帶來了問題，Rx 的排程器就是一個典型的範例。`NewThreadScheduler` 在不允許應用程式直接建立新執行緒的平台上應該做什麼？有一些替代方案，例如使用執行緒集區，但是如果您在不受限制的平台上執行，這些替代方案就不是最佳的。這導致必須在「使用令人不滿意的最低公分母」或「以某種方式安排 UWP 與其他平台的不同行為」之間做出選擇。

（較舊版本的 Rx 透過「平台啟發（platform enlightenments）」策略解決了這些問題，該策略能夠產生單一的核心 RX 二進位檔案集，以及可在執行階段探索的小型平台專屬元件，以提供所使用平台上的最佳實作。然而這項做法已被捨棄，部分原因是一連串不幸的事件：從 https://github.com/dotnet/reactive/issues/97 中描述的問題開始，接著需要修復該問題的第一個修復所產生的某些問題，如 https://github.com/dotnet/reactive/issues/199#issuecomment-266138120 所述。（順便提一下，由於支援的 .NET 平台範圍的變化以及 NuGet 的改進，導致這個問題的原始原因可能不再成問題了。）這就是為什麼今天主要的 `System.Reactive` 套件包含 UWP 目標的原因。）

微軟自己[撰寫 Windows 應用程式的指引](https://learn.microsoft.com/en-us/windows/apps/get-started/)極力淡化 UWP。在 2023 年 2 月可見的該頁面版本中，UWP 隱藏在「其他應用程式類型」區段的第四個也是最後一個索引標籤中。如果您顯示該索引標籤，它最後會警告您將無法存取較新的 Windows App SDK 中的 API，並鼓勵您使用 WinUI 而不是 UWP。它甚至進一步鼓勵您將現有的 UWP 應用程式遷移到 WinUI 3。

儘管如此，UWP 仍然受到支援，微軟也持續更新 UWP 的工具鏈。您可以在 Visual Studio 2022 中建立新的 UWP 應用程式。微軟確保許多函式庫和工具（包括他們自己的 MSTest 測試框架）在與 UWP 一起使用時能夠正確運作。然而，這很大程度上已是生命週期終點的支援：一切都可以運作，但沒有任何東西在更新。特別是，.NET UWP 應用程式的專案系統尚未更新為使用所有其他 .NET 專案都具備的現代 [.NET 專案 SDK](https://learn.microsoft.com/en-us/dotnet/core/project-sdk/overview) 系統。

這種缺乏 .NET 專案 SDK 支援的情況使得 UWP 成為像 Rx 這樣多目標函式庫的巨大痛點。

.NET SDK 樣式的專案可以是*多目標*的，這意味著它可以建立針對多個目標架構 Moniker（TFM，例如 `netstandard2.0` 和 `net6.0`）的 NuGet 套件。然而，如果您嘗試包含 UWP 專屬的 TFM（例如 `uap10.0`），您將面臨一系列令人困惑且棘手的建構錯誤，因為微軟尚未完成在 .NET SDK 專案系統中提供完整 UWP 支援所需的工作。處理這個問題的一種方法是使用 Claire Novotny 開發的 [MSBuildSdkExtras](https://github.com/novotnyllc/MSBuildSdkExtras) 專案。該專案在使工具執行它們並非真正想執行的工作（即以 UWP 為目標）方面做得非常出色，但它永遠無法做到完美，因為它試圖提供實際上應該是工具本身內建的功能。例如，[MSBuildSdkExtras 讀我檔案](https://github.com/novotnyllc/MSBuildSdkExtras/tree/b58e1d25b530e02ce4d1b937ccf99082019cdc47#important-to-note)指出，如果您使用此專案，就無法在命令列執行 `dotnet build`；您必須改為執行 MSBuild。

在 .NET 專案 SDK 環境中缺乏對 UWP 的官方支援，也是上述至少一個建構問題的背後原因。從根本上說，要讓 UWP 在這個環境中運作需要一些技巧性的修改，因此有一些功能無法完全正常運作。

UWP 在 .NET 生態系統中也沒有得到廣泛支援。在目前版本的 Visual Studio 上似乎無法將 xUnit 與 UWP 一起使用。我們似乎只有兩個選擇：放棄對 UWP 的支援，或者從 xUnit 轉向 MSTest。

既然它造成了所有這些問題，那麼如果微軟強烈不建議使用它，並推動人們轉向 WinUI，我們到底為什麼還要支援 UWP 呢？

### 為什麼在 2020 年支援 UWP？

早在 Rx 5.0 發布時，對 UWP 支援的需求更加強烈，因為現在 2023 年推薦的 WinUI 函式庫在當時相對較新。對於在 .NET 中建構利用 Windows 透過其 WinRT 樣式 API 所公開功能的 Windows 應用程式而言，UWP 是最實用的選擇。例如，如果您想撰寫一個可以透過 Windows 市集提供的 .NET 應用程式，並且該應用程式使用了相機，您就必須使用 UWP。

由於在許多情境下 UWP 是唯一實用的選擇，因此在當時放棄對它的支援是完全不合適的。

不太清楚的是為什麼在 Rx 5.0 中無法透過 .NET Standard 2.0 提供 UWP 支援。在 Rx 首次引入 UWP 支援時這是不可能的，原因就是前面描述的最低公分母問題。多年來，撰寫沒有特殊 UWP 支援的單一目標 `System.Reactive` 函式庫會在某些平台上產生次佳的體驗，或者可能在 UWP 上產生損壞的體驗。然而，這種情況在 2017 年隨著 Windows 10「秋季創作者更新」（版本 1709）而改變。從該版本開始，UWP 提供了對 .NET Standard 的完整支援，這意味著實作了在早期版本中被禁止的各種執行緒 API。最後一個**不**支援此功能的 Windows 版本（版本 1703）已於 2018 年 10 月停止支援，這意味著 Rx v4（2018 年 5 月首次發布）不能依賴它，但是到了 2020 年 11 月 [Rx.NET v5.0.0](https://github.com/dotnet/reactive/releases/tag/rxnet-v5.0.0) 發布時，.NET Standard 2.0 已經在所有仍受支援的 Windows 版本上的 UWP 中可用超過兩年了。

### 為什麼在 2023 年支援 UWP？

自 Rx 5.0 發布以來已經過去兩年多了。微軟極力反對使用 UWP，那麼為什麼我們仍然以它為目標呢？一個顯而易見的答案是，在這段時間內沒有新的 Rx 版本發布。然而，事情並沒有那麼單純。

儘管微軟強烈推動人們轉向 WinUI v3 的方向，但事實上，如果您今天想撰寫一個 .NET Windows 市集應用程式，某些 Windows 功能只有在您以 UWP 為目標時才能使用。例如，對相機的完整存取權限（包括直接存取擷取影像的原始像素）目前（2023 年 2 月）僅在 UWP 中可行。

我們非常希望能徹底移除 Rx 中所有 UWP 專屬的程式碼，因為這將簡化建構流程並修復許多問題。但是，由於開發人員有時仍然別無選擇只能使用 UWP，因此 Rx 需要繼續在 UWP 上運作。然而，值得注意的是這兩件事並不相同：

1. 支援 UWP
2. 在 `System.Reactive` 中提供 UWP 專屬的目標

我們認為 1 仍然是必要的，但我們更希望停止執行 2。我們將提供對 UWP 的完整支援，但理想情況下，我們會將所有 UWP 專屬的程式碼從主要方案中分離出來。不幸的是，少量的 UWP 專屬 API 介面已經滲透進了 `System.Interactive`。（`ThreadPoolScheduler` 在 UWP 目標中看起來略有不同，因為它提供了讓您可以設定其應使用的 [`WorkItemPriority`](https://learn.microsoft.com/en-us/uwp/api/windows.system.threading.workitempriority) 和 [`WorkItemOptions`](https://learn.microsoft.com/en-us/uwp/api/windows.system.threading.workitemoptions) 的屬性。）我們目前的看法是，既然這已經代表了 UWP 目標的 API 介面與所有其他目標之間的差異，那麼為了從 `System.Reactive` 中移除 UWP 專屬目標，容忍僅影響 UWP 程式碼的重大變更（breaking change）是值得的。但無論我們如何實現它，我們都必須以某種方式在接下來的至少幾個版本中繼續提供在 UWP 上執行的支援。

我們已經製作了一個原型，展示了如果分離 UWP 部分，Rx 可能會是什麼樣子：https://github.com/idg10/reactive/pull/3。由於這從 `System.Reactive` 中移除了 UWP 目標，因此對 UWP 用戶端包含了一項重大變更：他們會發現 `ThreadPoolScheduler` 現在看起來與所有其他 Rx 用戶端可用的排程器完全相同；如果他們需要舊功能，可以透過 `System.Reactive.Windows.Threading` 函式庫中新的 `WindowsThreadPoolScheduler` 來取得，除了名稱之外，它與舊的 UWP 專屬 `ThreadPoolScheduler` 完全相同。


## 即將發布版本的計畫

我們需要決定是應該嘗試一步解決所有問題，還是產生一些過渡版本以引導我們逐步走向解決方案。我們目前的立場是不會嘗試一次完成所有事情。我們希望盡快讓針對 .NET 6.0 和 .NET 7.0 的自動化測試就緒，以便驗證這些平台受到支援。（這必然需要修復阻止使用最新工具版本建構 Rx 的問題。）而且我們希望盡快提供 AsyncRx.NET 的預覽版本。

圍繞 UI 框架相依性的問題可以說更加棘手，因為解決這些問題必然會帶來更大的破壞性。解決程式碼膨脹問題將意味著確保以某些 Windows 專屬 TFM 為目標的專案不會僅僅因為使用 Rx 就自動獲得 WPF 和 Windows Forms 支援。這似乎需要是一項重大變更（除非我們將所有 Rx 移至某些全新的 NuGet 套件中，並將現有的 `System.Reactive` 套件轉變為僅為了向下相容性而提供的 facade）。此外，圍繞此問題存在各種微妙的細節，我們需要確保不會導致任何回歸（regression）。例如，我們需要確定不會重新引入舊的錯誤（https://github.com/dotnet/reactive/issues/97），在該錯誤中，外掛程式主機（尤其是 Visual Studio）可能會載入對於載入 `netstandard2.0` 還是 `net4x` 版本的 Rx 具有不同意見的不同外掛程式，從而導致無法解決的衝突和執行階段錯誤。我們還需要避免重蹈導致 https://github.com/dotnet/reactive/issues/199#issuecomment-266138120 中問題的覆轍。我們不想在測試針對此問題的策略時延誤其他所有事情。此外，現在有許多 .NET 框架（包括但不限於 Avalonia、Unity、Xamarin、WinUI），我們希望確信能與它們良好搭配運作。因此，儘管我們希望盡快解決這些特定問題，但我們認為這需要時間，並且不想延遲其他目標。

### Rx v6.0
首要任務必須是更新建構系統，以便可以使用目前的開發工具進行 Rx 的開發工作。如果無法開發 Rx，我們就無法修復其他問題。這將需要移除較舊且不受支援的目標。因此，下一個版本可能會以以下目標為主：

* `net6.0`（測試專案也以 `net7.0` 為目標）
* `net6.0-windows.XXXXX`，最有可能使用以下版本之一：
  * `net6.0-windows.18362`，我們可以使用 VS 2022 設定目標的最舊 TFM，對應於 Windows 10 版本 1903（於 2019 年 5 月發布，並於 2020 年 11 月停止支援）
  * `net6.0-windows.19041`，與 Rx 5.0 中相同的 Windows 版本（以 `net5.0-windows.19041` 為目標），對應於 Windows 10 版本 2004（於 2020 年 5 月發布，並於 2021 年 12 月停止支援）
  * `net6.0-windows.10.0.20348`，目前仍受支援的所有 Windows 10 和 Windows 11 版本均支援的最舊 SDK 版本（這意味著這是我們可以在仍然支援所有仍在受支援狀態的 Windows 版本的同時設定為目標的最新版本）
* `net472`
* `netstandard2.0`
* `uap10.0.XXXXX`，以下版本為顯而易見的候選對象：
  * ~~`uap10.0.16299`~~：這是 Rx 5.0 的目標版本，但 Visual Studio 2022 不支援 Windows 10 SDK 10.0.16299，因此這不是一個選項
  * `uap10.0.18362`：如上所述，這是目前工具鏈中最舊的選項
  * `uap10.0.20348`：如上所述，這是適用於目前受支援之所有 Windows 版本的最新版本

除非 xUnit 很快更新其對 UWP 的支援，否則我們很可能會將 xUnit 取代為 MSTest，因為這似乎是讓 UWP 單元測試能夠執行的唯一途徑。

我們應該考慮是否有容易解決的 .NET 6.0 相關問題應該包含在第一個版本中，包括：

* https://github.com/dotnet/reactive/issues/1683 - 將組件標記為可修剪（trimmable）

由於我們希望迅速完成此版本的發布，我們不想讓它依賴於修復每個懸而未決的問題，但是一旦 v5.1（或類似版本）就緒，我們就可以在解決下述發布版本的同時，考慮在後續的 v5.1.x 版本中修復懸而未決的錯誤。如果我們最終確實需要在下一個主要版本中進行重大變更，我們將希望繼續這樣做——如果事實證明無法在分離 UI 框架的套件之上提供向下相容的 facade，我們將希望保持此 v5.1（或類似版本）系列作為受支援的發布版本，以供無法或不想遷移到較新版本的使用者使用。

有關如何達成這第一步的更詳細說明，請參閱 [ADR 0001-net7.0-era-tooling-update](./adr/0001-net7.0-era-tooling-update.md)。

請注意，此版本的版本號碼 v6.0 聽起來好像與 .NET 6 有某種關聯，這純屬巧合。事實上我們在此版本中也支援 .NET 7。（不需要 `.net7.0` TFM，因為 `net6.0` 目標在 .NET 7 上可以完美執行，而且此版本不會使用任何 .NET 7 專屬的功能。）我們之所以提高主要版本號碼，是因為我們正在放棄對某些舊 TFM 的支援，這似乎是一個足夠重大的變更，值得給予一個新的主要版本號碼。（除了放棄對本身已不受支援的執行階段的支援之外，無意進行任何其他重大變更。）

### Rx.Async

我們希望盡快提供 Rx.Async 的預覽版本。我們不知道有任何技術原因需要將其與前一區段中描述的發布版本綁定。長遠來看，隨著較舊的 TFM 失去支援，我們預計可能會需要新的 Rx.NET 和 Rx.NET.Async 版本，而且我們可能會保持主要版本號碼同步，以明確表明這兩個函式庫處於同一時代。但除此之外，沒有理由將這兩個函式庫的發布緊密聯繫在一起。（錯誤修復和新功能可能會針對每個函式庫獨立發布。）此外，由於 Rx.Async 目前處於預覽狀態，即使這是一個長期目標，我們也不想現在就將它們統一——盡快提供 `alpha` 建構版本會更好。因此，執行這項工作可以與前一區段中描述的工作同時進行。

### Rx v7.0

在此版本中，我們希望解決 Avalonia 和其他 UI 框架所遇到的程式碼膨脹問題。我們認為這將需要把所有 UI 框架專屬的程式碼移至獨立的元件中。（這只是[大統一](https://github.com/dotnet/reactive/issues/199)的部分還原——我們不會恢復分離為 interfaces、core 等等的方式。）

我們還希望使第三方能夠產生自己與 Rx 的整合，並使這些整合能夠與 WPF、Windows Forms 和 UWP 整合一樣良好地運作——如果可能的話，我們希望避免某些 UI 框架享有特權的情況。與此相關的是，我們想認真考慮拆分 Rx 存放庫。確保第三方框架不會淪為二等公民的一種方法，是使我們自己的 UI 框架支援以相同的方式運作。（這樣做的另一個動機是，我們非常希望從主要 Rx 存放庫中移除所有 UWP 的痕跡，因為 UWP 工具鏈的糟糕狀態意味著只要有 UWP 存在，就往往會帶來麻煩。）我們需要解決圍繞測試的一些問題：我們如何確保主要存放庫中的變更不會導致某些框架中發生未察覺的失敗？我們如何為需要在不同平台上執行測試的框架提供核心測試套件？（如今，UWP 測試是透過將主要測試專案中的所有檔案連結到 UWP 測試執行器來實現的。如果 UWP 程式碼位於獨立的存放庫中，這將無法運作。）將 Rx 移至其自己的組織中，並為核心和框架專屬部分建立獨立的存放庫，也將使為文件和範例提供獨立的存放庫變得更加容易。


## 要測試的平台與框架

Rx 的使用非常廣泛，涵蓋許多不同風格的 .NET 和許多不同的框架。更新它的挑戰之一是我們可能會在不知不覺中破壞某些情境。因此，整理一份框架清單是個好主意，儘管我們沒有為其建構任何特定支援，但它們應該能夠透過 Rx 的其中一個 TFM 毫無問題地使用 Rx。任何 Rx 發布版本的品質標準之一應該是：我們確信它可以從這些框架中的任何一個使用而不會出現問題。

這不是一份詳盡的清單，但它應該包括：

* Avalonia
* Unity
* Xamarin
* WinUI
* Visual Studio 外掛程式
* MAUI
* Blazor
* Uno

顯然，WPF、Windows Forms 和 UWP 支援也很重要，但由於我們已經為這些提供了特定於框架的功能，因此它們有所不同。此清單適用於我們不打算為其提供任何明確功能，但仍希望能夠正常運作的平台。
