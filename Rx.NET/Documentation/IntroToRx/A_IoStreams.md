# 附錄 A：傳統 IO 串流有什麼問題

在[關鍵型別](02_KeyTypes.md#串流又如何)一章中，我指出 `System.IO.Stream` 不適合為我們在 Rx 中使用的那種事件串流進行建模。本附錄解釋了原因。

`System.IO.Stream` 所代表的抽象被設計為作業系統使應用程式程式碼能夠與可以接收和/或產生位元組串流的裝置進行通訊的一種方式。這使得它們成為在設計此類串流時常見的[開盤式磁帶儲存裝置](https://en.wikipedia.org/wiki/IBM_7-track)的良好模型，但如果您只想表示值序列，則顯得不必要地麻煩。多年來，串流已被挪用來表示越來越多樣化的事物，包括檔案、鍵盤、網路連線和作業系統狀態資訊，這意味著當 .NET 在 2002 年問世時，其 `Stream` 型別需要多種功能的混合以適應一些相當多樣化的情境。而且由於並非所有串流都相同，因此其中某些功能在某些串流上無法運作是相當常見的。

IO 串流旨在支援相當大量的位元組資料的高效傳遞，通常與本質上以大區塊處理資料的裝置一起使用。在為其設計的主要情境中，讀取和寫入作業將涉及呼叫作業系統 API，這些 API 通常相對昂貴，因此基本讀取和寫入作業期望使用位元組陣列。（如果您進行一次系統呼叫來傳遞數千個位元組，則該單次呼叫的額外負荷遠低於一次處理一個位元組的情況。）雖然這有利於提高效率，但對於開發人員來說可能很不方便（如果您希望純粹使用串流來表示實際上不需要進行系統呼叫的同處理程序事件串流，並且因此無法享受這種效能/便利性權衡的好處，這會很令人惱火）。

對此有一個標準的權宜之計修復方法：向應用程式程式碼呈現串流的函式庫通常不直接表示底層作業系統串流。相反，它們通常是*緩衝的*（buffered），這意味著函式庫將執行相當大區塊的讀取，並將最近擷取的位元組保留在記憶體中，直到應用程式程式碼請求它們為止。這可以使諸如 .NET 的單位元組 [`Stream.ReadByte`](https://learn.microsoft.com/en-us/dotnet/api/system.io.stream.readbyte) 方法之類的方法相當高效地運作：對該方法的數千次呼叫可能只會導致對提供對串流所代表的任何實體裝置存取的作業系統 API 的一次呼叫。同樣，如果您將資料傳送到 IO 串流中，緩衝串流將等待，直到您提供了某個最小數量的資料（在某些 .NET `Stream` 中，4096 位元組是常見的預設值），然後才實際將任何資料傳送到其目的地。

但對於我們在 Rx 中表示的各類事件來源來說，這可能是一個嚴重的問題。如果 IO 串流刻意將您與資料的實際移動隔離開來，那可能會引入延遲，這在金融應用程式中可能是災難性的，因為在金融應用程式中，資訊傳遞和接收的延遲可能會產生巨大的財務後果。即使沒有直接的財務影響，這種緩衝對於表示使用者介面中的事件也是無益的。沒有人希望在應用程式開始對該輸入採取動作之前必須點擊按鈕數千次。

還有一個問題是您並不總是知道自己獲得了哪種類型的串流。如果您確切知道自己有一個代表磁碟上檔案的未緩衝串流（因為您自己建立了該串流），您通常會撰寫與知道自己擁有緩衝串流時截然不同的程式碼。但是如果您撰寫了一個接受 `Stream` 引數的方法，則不清楚您獲得了什麼，因此您不一定知道哪種編碼策略是最好的。

另一個問題是，因為它們是導向位元組的，所以不存在產生更複雜值的 `System.IO.Stream`。如果您想要一個 `int` 值的串流（這並不是一個比*位元組*值的串流複雜*得多*的概念），`System.IO.Stream` 對您沒有任何幫助，而且直到最近它甚至可能會阻礙您。如果您使用普通的 `Read` 或 `ReadAsync` 方法，您可以嘗試一次讀取四個位元組，但 `System.IO.Stream` 可以隨意決定它只傳回三個位元組。（允許串流以這種方式吹毛求疵的原因是，最初的設計假定串流代表某些可能固有地以固定大小資料單位運作的底層裝置。磁碟機和 SSD 無法讀取或寫入單個位元組；相反，每個操作都適用於整數個「磁區」，每個磁區長度為數百或數千位元組。因此，讀取操作可能根本無法精確提供您所要求的那麼多位元組。這也可能適用於表示透過網路傳入的資料的串流：此類串流可能已經接收了一些資料，但少於您的要求，並且它們可能決定傳回已經擁有的資料，而不是讓您等待下一條網路訊息到達。）現在由取用端程式碼負責解決如何處理該問題。.NET 7.0 最終透過新增 [`ReadExactly`](https://learn.microsoft.com/en-us/dotnet/api/system.io.stream.readexactly) 和 [`ReadExactlyAsync`](https://learn.microsoft.com/en-us/dotnet/api/system.io.stream.readexactlyasync) 方法修復了這個問題（在 `Stream` 首次出現大約二十年後），但是如果您必須以 .NET Framework 為目標，則這些方法不可用，您仍然必須完全自己解決這個問題。

即使您使用新方法（或者您撰寫包裝函式來處理由於 `Stream` 起源作為磁帶儲存裝置的抽象而引起的這些問題），仍然存在缺點。如果您希望型別系統幫助您區分 `int` 值的串流和 `float` 值的串流，`Stream` 不會對您有所幫助。您最終將需要一些具有型別參數的不同抽象。類似 `IObservable<T>` 的東西。我們確切知道期望從 `IObservable<T>` 獲得什麼形式的資料這一事實，對於使其支援的許多 LINQ 運算子變得實用至關重要。

混亂的另一個潛在根源是 Unix 的「一切皆檔案」設計特性。作業系統透過與檔案相同的作業系統抽象來表示各種事物，這簡化了作業系統設計，並且在某些情況下使您能夠以創造性的方式套用最初為檔案設計的工具。但缺點是有些串流很挑剔。從 .NET 型別系統的角度來看，可能會得到一個看起來與任何其他串流相同的串流，但該串流僅在您以某個特定大小的區塊讀取或寫入時才起作用。

相反，Rx 針對可觀察來源如何與其訂閱者互動嚴格定義的規則意味著我們確切知道自己的處境。

對於串流如何支援多個訂閱者沒有明確的模型。Unix `tail` 命令等程式能夠「追蹤」檔案的變更，但它們實現這一目標的方式絕不像兩個觀察者都呼叫 `Subscribe` 那麼簡單。

這些只是取用端的問題。如果您想將事件來源實作為 `Stream`，那也不會有太多樂趣。要實作您自己的衍生自 `Stream` 的型別，您需要實作它定義的所有十個抽象成員：5 個屬性和 5 個方法。這與 `System.Reactive` 提供的用於實作 Rx 事件來源的簡單方法相去甚遠。
